# Trusted parent-to-child provisioning

A parent agent can now onboard a new child without a person or UI. The parent must
already authenticate as a persisted principal and hold a live grant with delegation
depth remaining. The service creates no root authority and accepts no caller-chosen
child identity, organization, or role.

## Runtime flow

1. The parent runtime constructs a narrow `AuthorityScope` using the existing fields.
   Start with quote-only, zero-budget authority where that meets the task. Choose
   expiry no later than the parent and decrease delegation depth by at least one.
2. The trusted CLI generates a cryptographically random 256-bit child secret and
   persists it in a private file **before any provisioning request**. It sends only
   the SHA-256 verifier and a persisted idempotency key through MCP.
3. The authenticated parent calls `provision_child`. The canonical authority service
   validates scope, ancestor lifetime/revocation and remaining budget. One atomic
   transaction creates the principal, hashed key, child grant, idempotency binding,
   and `grant.issue` / `principal.provision` audit events.
4. The child runtime reads its own private file, authenticates with its distinct
   secret, and calls the same existing MCP tools. It cannot authenticate as its
   parent or read another organization's data.
5. The authorized parent can revoke the initial child grant. The bound key then
   fails authentication, including for already-connected clients. Descendant keys
   also fail when that ancestor chain is revoked or expires.

The fixed child identity is `kind:AGENT`, `role:SERVICE`, in the authenticated
parent's organization. The supplied credential verifier is a registration input,
never proof of an existing principal: the parent connection is authenticated and
the child identity is generated by the service. Only a runtime-generated high
entropy secret should be registered; models must not invent or receive secrets.
No raw child secret is sent to MCP, HTTP, tool output, `_meta`, logs, or analytics.
The database stores only its hash. The CLI returns safe principal/grant metadata
and the private file path, not its contents.

## Commands

Use Node 24 from the repository root. The parent runtime injects its own
`AGENT_API_KEY` through its secret environment. `MCP_PUBLIC_URL` names the intended
MCP endpoint. Prepare an existing private runtime directory outside the checkout;
`child-scope.json` contains the exact scope to delegate.

```sh
npm run --silent agent:provision -- --url "$MCP_PUBLIC_URL" \
  --parent-grant "$PARENT_GRANT_ID" \
  --scope-file ./child-scope.json \
  --credential-file "$PRIVATE_RUNTIME_DIR/child.json"

# Launch this in the child runtime; it selects the child file explicitly.
npm run --silent agent:onboard -- \
  --credential-file "$PRIVATE_RUNTIME_DIR/child.json"
```

The file is created exclusively with mode 0600, fsynced before the request, and
never overwritten. Existing files must be regular, private, owned by the current
runtime, outside the repository, and match the original endpoint/parent/scope.
Symlinks and unsafe permissions are rejected. The file contains the secret,
endpoint, and retry inputs; its contents must remain outside model prompts and
terminal output. Transfer it to another host only through the orchestrator's
existing private secret-distribution channel. This change does not add one.

The child onboarding command never falls back to an inherited parent credential.
It also refuses to forward the child secret to a different endpoint. The CLI
neither spawns an LLM worker nor purchases automatically. A trusted supervisor can
launch a child process with this file or privately inject the secret into that
child's environment. Native MCP runtimes can implement the same verifier protocol
using their own secret store without using the CLI or a filesystem.

On a lost response, run the identical provisioning command with the **same files**.
It returns the same principal and grant. Do not delete/recreate a credential file
or choose a new idempotency key after an uncertain response; that could create a
second child. Changed retry input is rejected. Lost private secrets cannot be
recovered from the server; revoke the old grant and provision a replacement.

Creating multiple children does not multiply budget. All protected operations
retain the canonical ancestor reservation/debit checks and independent supplier
policy. The initial credential's expiry/revocation binding remains in force even
if a subsequent authority request produces an additional grant. Scope renewal
past that credential lifetime requires a new provisioned child; credential rotation
and principal re-use are outside this change.

## Persistence and deployment

`db/schema.sql` and `db/schema.postgres.sql` add `child_provisionings`. It binds an
authenticated parent's idempotency key to the exact request and the issued child,
grant and key. PostgreSQL keeps it in private `agentpass`, enables RLS and revokes
PUBLIC table privileges. No public Data API policies are added.

For a hosted deployment, apply the updated schema using the existing private
`npm run setup:postgres` administrative workflow **before deploying this code**.
That workflow preserves existing grants, keys and ledgers. Authentication now
consults this table; deploying first would fail closed while it is missing.
No hosted migration or production deployment was performed for this feature.
The production branch auto-deploys, so review and order this rollout explicitly.
The PostgreSQL schema/security approach was checked against the current
[official RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Verification

- Positive/negative service tests cover authenticated ownership, server-chosen
  identity, each scope dimension, depth, effective budget including reservations,
  duplicate verifiers, invalid input and forbidden role/tenant/identity fields.
- Identical concurrent retries create one child. Altered retry input is denied.
  An injected persistence failure after grant issuance rolls back principal, key,
  grant, provisioning record and audit events together.
- Every child authentication checks its initial chain. Direct/ancestor revocation,
  expired child/parent scope, inactive identity and database failure fail closed.
- Private file tests cover mode 0600, reuse, no overwrite, symlinks, unsafe modes,
  repository destinations, endpoint substitution and no parent-key fallback.
- Real CLI subprocesses against SQLite and a fresh local PostgreSQL database create
  a child, replay provisioning, onboard that child despite an inherited parent
  environment key, quote/purchase, provision a quote-only grandchild, and verify
  revocation disables both child and grandchild keys. Tool discovery covers all
  ten tools, including the existing stdio/remote adapter callers.
- A separate no-browser proof used the unchanged real simulated supplier: a new
  child received a $900 grant, obtained the authoritative $850 quote, completed one
  simulated purchase, showed $50 effective child budget, and failed authentication
  after parent revocation. CLI/MCP outputs did not contain its secret. This used
  fresh disposable local databases and no hosted allocation.

Root-owner provisioning remains an administrative trust anchor. Once a parent has
that initial trusted identity and a delegable grant, child creation, negotiation,
execution, and revocation can all run without a person or browser.
